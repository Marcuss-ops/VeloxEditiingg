# Multi-Scene Concat Smoke — Operator Run Report

**Date:** 2026-07-28
**Harness:** `tests/smoke/full_payload/multi_scene_concat/run.sh`
**Commit series:** atomic C1 (smoke harness + payload builder ext) + C2 (this doc)

## TL;DR

A re-runnable smoke that submits a `>=10`-scene real-asset payload to the
Velox Master pinned to a single worker, polls until `SUCCEEDED`, and
verifies **T1 state machine** + **T2 duration coherence** + **T3 Drive
delivery** + **T4 worker pin** + **T5 CPU/RAM/disk** measurement.

Sibling to `tests/smoke/full_payload/run.sh` (4-scene full-payload smoke)
and `tests/worker-cert/smoke_one.sh` (2-scene per-worker cert smoke).
This harness is the third tier in the canonical smoke matrix and exercises
the scene-concat engine path that the 2-scene and 4-scene smokes
under-stress.

## What the smoke verifies

| Tier | Verifies | Mechanism |
|---|---|---|
| **T1** | `SUCCEEDED` reached via the master state machine | poll `GET /api/v1/jobs/{job_id}` until `.status == SUCCEEDED` (1→2→4→8→16s exp backoff, cap `MULTISCENE_POLL_TIMEOUT_S=600`) |
| **T2** | duration coherence (sum of `scene.duration_seconds` vs measured output `duration_seconds` via `ffprobe`) | download artifact via bearer-authed `artifact_url`, run `ffprobe -show_format`, compare against expected `± max(500ms, 5%)` |
| **T3** | Drive delivery to the explicitly selected destination destination | `status == SUCCEEDED` ⇒ all `delivery_plan` entries committed (canonical monotonic guarantee per `SubmitJobStatusResponse`) **and** `artifact_size_bytes > 0` (HEAD probe via `smoke_artifact_size`) |
| **T4** | placement-pin enforcement | scrape master log line `TaskLeaseGranted sent to worker <ID> (...) task=<TID> job=<JID> attempt=<AID> lease=<LID>` via `smoke_scrape_lease`; fallback to `current_task_id` race-prone check |
| **T5** | CPU/RAM/disk | snap `GET /api/v1/workers/{id}` BEFORE submit, snap AFTER `SUCCEEDED`, report `disk_used_bytes`, `cpu_utilization_ratio`, `memory_used_bytes` deltas |

## Design decisions

### D1. Modulo-cycle scene generation via extended `build_real_payload.py`

The canonical payload builder (`tests/worker-cert/build_real_payload.py`)
was extended with two new flags:

- `--scenes-count=N` (default 2, matches canonical `smoke_one.sh` shape)
- `--duration-per-scene=N` (default 3, matches canonical `smoke_one.sh`)

The extension is **backward-compatible**: default `2` and `3` keep the
existing 2-scene payload byte-identical. The multi-scene smoke uses
`--scenes-count=10 --duration-per-scene=2` to exercise the concat engine
path under `~20s` total expected duration, well within the
`MULTISCENE_POLL_TIMEOUT_S=600` budget.

Scenes are generated by modulo-cycling through
`tests/worker-cert/fixtures/assets.json`:

```python
scenes[i].clip_link     = velox-asset://<clips[i % len(clips)]>.asset_id
voiceover_paths[i]      = velox-asset://<voiceover[i % len(voiceover)]>.asset_id
```

Pure-cycle (i → i % n) is intentionally simple. The canonical chain
(`enqueue.go` → `normalize.go`) does not require per-scene uniqueness
of `clip_link` references; only that each `velox-asset://<asset_id>`
resolves to a known asset_id.

### D2. Single-worker pin via env var + executor-id + post-hoc scrape

Three layers of pin enforcement:

1. **Env var**: `export VELOX_PLACEMENT_PIN_WORKER_ID=<id>` is exported
   by `run.sh` before any curl call. Per `build_real_payload.py` §build_payload
   comment: *"On master deployments WITH env var
   VELOX_PLACEMENT_PIN_WORKER_ID, this is doubly-pinned: same executor
   AND same worker."*
2. **Executor-id**: `target_executor_id=scene.composite.v1@1` is stamped
   into the payload explicitly (does NOT rely on the placement
   matcher's default derivation; canonical chain referenced in
   `DataServer/internal/jobs/enqueue/normalize.go`).
3. **Post-hoc scrape**: after `SUCCEEDED`, the harness scrapes the master
   log for the `TaskLeaseGranted sent to worker <ID>` line and asserts
   `<ID>` matches `<worker_id>`. Fallback to `current_task_id` when
   log-scrape returns an empty worker_id (race-prone but covers log-rotation
   gaps).

### D3. Forbidden-pattern self-check is a single-source regression shield

The harness delegates payload construction to `build_real_payload.py
--strict`, which already runs `assert_no_forbidden` (Python regex walk over
JSON leaves). For belt-and-suspenders, the harness ALSO runs an inline
bash `assert_no_forbidden` (jq-based regex walk). Both checkers look for:

```
velox-asset://(voiceovers|clips|subtitles|images)/<file>.<ext>
file://
```

A regression in one that the other would still catch is improbable, but
defense-in-depth is cheap. The two checkers cross-validate each other.

### D4. CPU/RAM/disk measurement is sampler-derived, not realtime

The harness uses `GET /api/v1/workers/{id}` → `Metrics` map. Per
`DataServer/internal/handlers/server/api/workers_dto.go`, the typed
`WorkerMetrics` struct exposes `cpu_utilization_ratio`, `memory_used_bytes`,
`disk_free_bytes`, `process_rss_bytes`, `load_average` — all sampler-derived
(snapshot, not realtime). The harness records both BEFORE-snap and
AFTER-snap in the evidence JSON envelope.

**Known limitation:** sampler-derived means there can be jitter — a
`cpu_utilization_ratio` of `0.42` BEFORE submit and `0.45` AFTER doesn't
imply a +0.03 spike was caused by the smoke (other workers' renders or
the OS scheduler can interleave samples). For a true peak measurement,
the operator can cross-reference `task_attempt_metrics.peak_rss_bytes` and
`task_attempt_metrics.cpu_percent_peak` per attempt (via the master
`attempt_id` from the lease scrape). **This is a follow-up** — the
canonical "peak per attempt" endpoint is not currently exposed on a
public master route; the `worker_metric_samples` table is the source of
truth, queryable via `store.ListWorkerMetrics`.

### D5. Duration coherence tolerance: `± max(500ms absolute, 5% relative)`

For a 10-scene × 2s payload (20s expected), absolute floor (500ms)
dominates: passes if measured is in `[19.5s, 20.5s]`. For longer payloads
(50-scene × 4s = 200s expected), relative (5%) dominates: passes if
measured is in `[190s, 210s]`. Frame-alignment padding can add up to
~33.3ms/scene at 30fps (max ~333ms drift over 10 scenes), so 500ms is
a defensible floor.

### D6. Drive delivery verification is via canonical `SubmitJobStatusResponse`

Per the openapi `SubmitJobStatusResponse` contract: `status=SUCCEEDED` is
the canonical monotonic guarantee that (a) the artifact has been committed
to its destination and (b) all `delivery_plan` entries reached `SUBMITTED`
state. The harness asserts `status == SUCCEEDED && artifact_size_bytes > 0`
to confirm Drive delivery to the explicitly selected destination.

**Known limitation:** `status=SUCCEEDED` does NOT expose per-destination
delivery status — only that ALL `delivery_plan` entries are committed.
A per-destination split (e.g., "Drive SUCCEEDED but S3 FAILED") is NOT
distinguishable from "all SUCCEEDED". Per-destination split is a
follow-up that would require a new master endpoint.

## Verification matrix

| Tier | Pre-condition | Verifies | Tolerance |
|---|---|---|---|
| T1 | master reachable | poll until SUCCEEDED | exp backoff 1→16s, cap 600s |
| T2 | artifact_url accessible | `\|measured - expected\|` | `± max(500ms, 5%)` |
| T3 | SUCCEEDED + artifact_size > 0 | all delivery_plan entries committed | n/a |
| T4 | log scrape returns worker_id | lease issued to `<worker_id>` | exact match |
| T5 | worker_id reachable | metric delta recorded | n/a (informational) |

## Known limitations

1. **Sampler-derived metrics** (D4): jitter can mask single-job peaks.
   True peak requires `task_attempt_metrics` per-attempt query — a
   follow-up that needs a new master endpoint.
2. **Per-destination delivery split** (D6): `status=SUCCEEDED` aggregates
   all `delivery_plan` entries. Per-destination split is a follow-up.
3. **Artifact download auth**: `--artifact-verify=1` uses the M2M bearer
   to download the artifact body. If the master returns an externally-
   signed URL (e.g., Drive), the bearer may not work and T2 falls back
   to `SKIPPED`. Documented in the README.

## Run examples

```bash
# Selftest (no HTTP) — payload shape + forbidden-pattern check
tests/smoke/full_payload/multi_scene_concat/run.sh --mode=selftest

# Dry run (no HTTP) — build payload + jq summary
tests/smoke/full_payload/multi_scene_concat/run.sh --mode=dry

# Full submit
VELOX_MASTER_URL=https://velox.example.com \
VELOX_ADMIN_TOKEN=$(cat ~/.config/velox/admin-token) \
MULTISCENE_TARGET_WORKER_ID=host_57_131_20_173 \
tests/smoke/full_payload/multi_scene_concat/run.sh

# Custom: 12 scenes × 3s = 36s expected
tests/smoke/full_payload/multi_scene_concat/run.sh \
  --worker-id host_57_131_20_173 \
  --scenes-count=12 \
  --duration-per-scene=3 \
  --artifact-verify=1
```
